## 排查 EC2 公网访问失败（54.254.154.60）

**现象**：内网 `curl http://172.31.47.77/health` 返回 200，但公网 IP 浏览器/curl/postman 全部 ERR_EMPTY_RESPONSE。worker 容器显示 unhealthy。

**根因**：AWS 安全组未开放 80/443 端口。外部 4 节点（加拿大/塞浦路斯/以色列/伊朗）实测 80、443 全部 `Connection timed out`，而 22 端口 0.26s 连通 → 差分证明是安全组缺规则，非应用层问题。应用侧全部健康：nginx 监听 0.0.0.0:80、容器间 api:8000 返回 `{"status":"ok"}`、api 容器 healthy。

**关键陷阱（重要，以后排障必记）**：
- 本机 Mac 跑在 TUN 代理下（源地址显示 `198.18.0.0`），`curl` 打印的 "Connected to 54.254.154.60 port 80" 是**代理伪造的假象**。连 `1.1.1.1:9999` 都"连通"。本地端口探测全部不可信。
- 正确做法：用 check-host.net 等**真实外部节点**做差分测试（`https://check-host.net/check-tcp?host=IP:PORT` + Accept: application/json），或 SSH 进 EC2 用 `aws`/IMDSv2 查。
- EC2 上无 AWS 凭证（`aws` CLI 存在但 `Unable to locate credentials`），本机也没装 aws cli → 开放安全组需用户在自己配好凭证的机器上执行。
- SSH 可用密钥：`~/.ssh/smartdocs-ai-key.pem`（`aws-ec2.pem` 也能连上）。`~/.ssh/config` 里的 `ec2-host`(13.229.203.118) 已失效。

**附带问题**：worker 是 arq 进程不监听 HTTP，但镜像 Dockerfile 带 `HEALTHCHECK CMD curl localhost:8000/health`（第 56-57 行），对 worker 必然失败。`docker-compose.prod.yml` 已写 `healthcheck: disable: true`，但运行中的容器仍是旧配置（nginx 端口映射也仍是旧的 `{"80/tcp"}`，没有 443）→ **改了 compose 必须 `--force-recreate` 才生效**。

**产出**：`scripts/fix-public-access.sh`（check / apply 两种模式，先开放安全组 80，443 交互确认，再 SSH 重建 worker+nginx 容器）。已过 `bash -n` 语法校验。本机无 aws cli 时正确提示。

**未完成**：安全组实际开放需用户执行 `./scripts/fix-public-access.sh apply`（需其 AWS 凭证）。

## 架构决策：安全组不能写进 docker-compose（同日）

用户问"能否直接改 docker-compose.yml，这样换机器部署更方便"。结论是**不行，属架构边界**：
- 安全组在 AWS VPC 控制面，compose 无调用 AWS API 的能力；
- 时序上也不可能——安全组必须在实例启动**前**放行 80，而 compose 在实例起来后才跑。

**分层方案（已实施，让"换机器"真正自动化）**：
1. `scripts/ec2-user-data.sh`：新增 7b 步骤，用 IMDSv2 token 取 instance-id → 查 SG → `authorize-security-group-ingress` 开放 80（`SG_CIDR` 可覆盖，默认 0.0.0.0/0）。无实例角色时不失败，只打印 `ACTION REQUIRED` 提示。顺带修正该文件里 `AWS_REGION` 默认值 `us-east-1` → `ap-southeast-1`（与实际不符）。
2. `docker-compose.prod.yml`：nginx 加 `post_start` 钩子做公网可达性体检（需 Compose v2.30+，EC2 实测 v5.6.0 满足）。
3. `scripts/deploy.sh`：新增 `verify_public_reachable()`，部署成功后经第三方节点外部探测，失败时明确提示安全组。步骤编号 /5 → /6。
4. `DEPLOY.md`：补"容器正常但公网访问不了"排查章节 + 两个 AWS 限制说明。

**重要发现：`deploy.sh` 原有的健康检查有盲区**。它打 `HEALTH_URL=http://localhost/health`（内网），公网断掉时照样返回 200 → 会报"部署成功"但用户完全访问不了。这正是本次故障两天没被发现的原因。

**两个必须记住的 AWS/本地环境限制**：
- **EC2 不能 curl 自己的公网 IP**（AWS 不支持 hairpin NAT，实测 `self_public=000`）。所以服务器上永远无法自检公网，必须借第三方节点（check-host.net）外部探测。
- **本机 Mac 在 TUN 代理下**，源地址显示 `198.18.0.0`，`nc`/`curl` 的 "Connected" 是伪造的（连 `1.1.1.1:9999` 都"通"）。本地探测一律不可信。
- check-host.net 用法：`https://check-host.net/check-http?host=<urlencoded>&max_nodes=2`（带 `Accept: application/json`）拿 request_id → 等 10s → `https://check-host.net/check-result/<id>`。已在本机与 EC2 双侧实测通过，EC2 上能正确判出 "Connection timed out"。

## 补充发现（同日晚间）

**1. 两个后台任务卡死的真实原因（不是网络问题）**：
`docker exec nginx wc -l /var/log/nginx/access.log` 会**永久挂起**——因为官方 nginx 镜像里 access.log/error.log 都是指向 `/dev/stdout`、`/dev/stderr` 的**符号链接**，读它们会一直等输出。命令跑了 1h37m 才因容器被重建而返回。
**教训**：查 nginx 日志一律用 `docker logs <container>`，不要 `docker exec` 去 read/cat 容器内日志文件。

**2. 容器在 15:29 被重建（不是我做的）**：
重建后 `worker` 的 healthcheck 变成 `Test=[NONE]`、`Health=DISABLED` → **unhealthy 误报已解决**，服务全部正常（内网 200）。触发原因疑似执行了带 `--force-recreate` 的 deploy（服务器 `scripts/deploy.sh` 处于 modified 状态且新增了未提交的 `.current_tag`），但脚本里不含 `verify_public_reachable`（grep 计数 0），说明**用的是旧版脚本**。

**3. 重要：本机改动尚未同步到服务器**。
服务器 `/opt/smartdocs/docker-compose.prod.yml` 仍是旧版：还有 `0.0.0.0:443:443`、没有 `post_start`（grep 计数 0）、文件时间 `Oct 9 10:41`。
服务器 git HEAD = `ec84545 github 测试库改为5432`，`git status` 显示 `M .env / M docker-compose.prod.yml / M scripts/deploy.sh / ?? .current_tag`。
**→ 下次部署前必须先 commit + push + 服务器 git pull**，否则本机修复不会生效。服务器上 443 端口已实际监听（无证书，握手会失败，属预期）。

**4. AWS 安全组结构（本机实测）**：
实例 `i-09fc0d2a5ceddba5b` → 弹性网卡 `eni-0d03a9d50cf8a6bb7`（子网 `subnet-0232158a3f60740e9`）→ 挂**两个**安全组：`sg-02b1e124a72cd0feb`（缺 80）、`sg-0c50bb792881a77ea`（有 22）。多个 SG 规则取**并集**，任一放行即通。
安全组绑在 ENI 而非实例上，创建时指定与事后修改**都支持且立即生效、无需重启**；但 **user-data 只在实例首次创建时跑一次，不会补跑**，所以已存在的机器必须单独开一次 80。
